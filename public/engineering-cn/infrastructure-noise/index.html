量化智能体编程评测中的基础设施噪声

发布于 2026 年 2 月 5 日

基础设施配置可使智能体编程基准的结果相差数个百分点——有时甚至超过排行榜顶尖模型之间的差距。

非官方中文译文，仅供个人或获授权的内部阅读。 查看英文原文

SWE-bench 和 Terminal-Bench 等智能体编程基准通常用于比较前沿模型的软件工程能力，排行榜上的领先位置往往只相差几个百分点。这些分数常被视为模型相对能力的精确度量，也越来越多地用于决定部署哪些模型。然而，我们发现，仅基础设施配置就足以造成超出这些差距的结果差异。在内部实验中，Terminal-Bench 2.0 上资源最充足与最受限配置之间的差距为 6 个百分点（p < 0.01）。

静态基准直接为模型输出评分，运行环境不会影响结果。智能体编程评测则不同：模型获得一个完整环境，可在其中编写程序、运行测试、安装依赖项，并在多轮交互中迭代。运行时不再是被动容器，而成为解题过程不可分割的一部分。资源预算和时间限制不同的两个智能体，实际上并未参加同一场考试。

评测开发者已经开始考虑这一点。例如，Terminal-Bench 2.0 在其最新的 2.0 版本中，为每项任务指定了推荐的 CPU 和 RAM。不过，指定资源并不等于始终如一地强制执行它们。而且我们发现，执行方法会改变该基准最终实际测量的内容。

问题的由来

我们在 Google Kubernetes Engine 集群上运行 Terminal-Bench 2.0。校准设置时，我们注意到分数与该基准的官方排行榜不一致，而且基础设施错误率高得惊人：多达 6% 的任务因 Pod 错误而失败，其中大部分与模型解决任务的能力无关。

分数差异源于执行方式。我们的 Kubernetes 实现将每项任务的资源规格同时视为下限和硬上限：每个容器都能保证获得指定资源，但一旦超过便会立即被终止。容器运行时通过两个独立参数执行资源约束：一个是保证分配量，即预先保留的资源；另一个是硬限制，容器达到该限制便会被终止。当两者设为相同值时，瞬时峰值没有任何余量：短暂的内存波动就可能因 OOM 而杀死本可成功的容器。为此，Terminal-Bench 的排行榜使用了另一家沙箱提供商；其实现更宽松，允许临时超额分配而不终止容器，以优先确保基础设施稳定性。

这一发现引出了一个更大的问题：资源配置会在多大程度上影响评测分数？

为量化脚手架的影响，我们在六种资源配置下运行了 Terminal-Bench 2.0：从严格执行每项任务的规格（1 倍，即同时作为下限和上限），到完全不设上限。其他一切保持不变：相同的 Claude 模型、相同的 harness、相同的任务集。

在实验中，资源余量越大，成功率越高。这主要由基础设施错误率在每一步都单调下降所推动：从严格执行时的 5.8%，降至不设上限时的 0.5%。严格执行与 3 倍余量之间的下降（5.8% 至 2.1%）在统计上显著，p < 0.001。余量更多时，因超出分配额度而被终止的容器更少。

从 1 倍到 3 倍，成功分数在噪声范围内波动（p = 0.40）。在 1 倍条件下崩溃的大多数任务，无论如何本来也会失败——这正是我们在数据中观察到的结果。智能体进行探索、撞上资源墙并被抢占，但它从未处于通向正确解的路径上。

然而从约 3 倍开始，这一趋势发生变化：成功率的上升速度快于基础设施错误率的下降速度。

从 3 倍到不设上限，基础设施错误率又降低了 1.6 个百分点，而成功率上升了近 4 个百分点。额外资源让智能体能够尝试只有在宽裕配额下才可行的方法，例如引入大型依赖项、生成代价高昂的子进程，以及运行内存密集型测试套件。在不设上限的资源条件下，相较 1 倍的总体提升为 +6 个百分点（p < 0.01）。在边际情况下，诸如 rstan-to-pystan 与 compile-compcert在获得更多内存余量后，其成功率显著提高。

这如何影响测量

在约 3 倍 Terminal-Bench 规格以内，额外资源解决的是基础设施可靠性问题，即瞬时资源峰值。Terminal-Bench 维护者使用的沙箱提供商正在后台隐式地实现这一点；评测变得更稳定，却不会变得更容易。

但超过 3 倍后，额外资源开始主动帮助智能体解决此前无法解决的问题，这表明资源限制实际上会改变评测所测量的内容。严格限制会无意中奖励资源效率极高的策略，而宽松限制更具包容性，会奖励能更好利用全部可用资源的智能体。

一个能极快写出精简高效代码的智能体，会在严格约束下表现出色。一个借助重量级工具暴力搜索解法的智能体，则会在宽松约束下表现出色。两者都是合理的测试对象，但若不说明资源配置就将它们压缩为一个分数，这些差异以及对现实世界的可泛化性都将难以解释。

在 bn-fit-modify 中，这是一项要求拟合贝叶斯网络的 Terminal-Bench 任务；某些模型的第一步是安装标准 Python 数据科学栈：pandas, networkx, scikit-learn, 及其完整工具链。在宽松限制下，这种方法行得通。在严格限制下，Pod 会在安装过程中耗尽内存，智能体甚至还没写出一行解题代码。确实存在更精简的策略（只用标准库从头实现数学计算），而有些模型默认就会采用它，另一些则不会。不同模型有不同的默认方法，资源配置决定了哪些方法恰好能够成功。我们在不同 Anthropic 模型上复现了这一核心发现。影响方向保持一致，但幅度有所不同。其他非 Claude 模型似乎也呈现相同趋势，但我们尚未进行严格测试。

我们还通过在 SWE-bench 上进行交叉实验，检验这种模式是否适用于 Terminal-Bench 之外的评测。我们在 227 个问题上、每个问题 10 个样本的条件下，将可用 RAM 总量提高至基线的 5 倍。结果仍然成立，尽管幅度较小：分数同样随 RAM 单调上升，但 5 倍时仅比 1 倍高 1.54 个百分点。SWE-bench 任务的资源密集程度较低，因此影响较小是预期之中的；但这也表明资源分配在此并非中性的。


其他方差来源

资源分配并非唯一的隐藏变量。在某些配置下，时间限制也开始发挥作用。

原则上，评测设置的每个要素都会影响最终分数：从集群健康状况到硬件规格，从并发级别到出口带宽。智能体评测在设计上就是端到端系统测试，系统中的任何组件都可能成为混杂因素。例如，我们曾观察到通过率会随一天中的时段而波动，这很可能是因为 API 延迟随流量模式和故障事件而变化。我们尚未正式量化这一效应，但它说明了更大的问题：“模型能力”与“基础设施行为”之间的边界，比单一基准分数所暗示的更加模糊。模型提供商可以通过专用硬件来保护其评测基础设施，但外部评估者难以轻易做到同样的事。

公开基准通常旨在测量纯粹的模型能力，但在实践中，它们可能将这种能力与基础设施特性混为一谈。有时这可能是可取的，因为它能对整个技术栈进行端到端测试；但更常见的情况并非如此。对于准备公开共享的编程评测，在多个时段和多个日期运行将有助于平均掉噪声。

我们的建议

理想情况下，每次评测都应在完全相同的硬件条件下运行——包括运行评测的脚手架和推理栈——这样可确保全面的完美可复现性。然而，这未必总是现实可行。

鉴于容器运行时实际通过保证分配量和单独的硬终止阈值来执行资源约束，我们建议评测为每项任务指定这两个参数，而非一个固定的单一值。单一精确规格会把保证分配量设为与终止阈值相同，从而没有任何余量：我们在 1 倍条件下记录到的瞬时内存峰值足以使评测不稳定。分开这两个参数，可为容器提供足够的缓冲空间，避免无故 OOM 终止，同时仍执行硬上限以防止分数虚高。

两者之间的区间应经过校准，使下限和上限处的分数彼此仅在噪声范围内不同。例如，在 Terminal-Bench 2.0 中，将上限设为每项任务规格的 3 倍，使基础设施错误率大约降低三分之二（5.8% 至 2.1%，p < 0.001），同时使分数提升保持温和且完全处于噪声范围内（p = 0.40）。这是合理的折中：在不消除有意义的资源压力的前提下，基础设施混杂因素基本被中和。确切倍数会因基准和任务分布而异，因此应予以报告；但经验校准的原则具有普遍性。

我们为何关注此事

这些发现的实际影响超出了评测基础设施。基准分数越来越常被用作决策依据，但这种日益增加的关注和依赖并不总是伴随着运行或报告方式上相应的严谨性。以当前情况而言，排行榜上领先 2 分，可能反映真正的能力差异；也可能只反映某次评测使用了更强的硬件，甚至是在更幸运的时段运行，或两者兼有。若未公开（或标准化）设置配置，外部人员很难判断，除非有兴趣的一方额外投入精力，在完全相同的条件下复现实证结果。

对于 Anthropic 等实验室，这意味着应将智能体评测的资源配置视为一等实验变量，并以与提示格式或采样温度同等的严谨性加以记录和控制。对于基准维护者，公开推荐的资源规格（正如 Terminal-Bench 2.0 所做的那样）会大有帮助；若再说明执行方法，便能弥合我们发现的缺口。对于任何使用基准结果的人，核心结论是：智能体评测中的小幅分数差异，其不确定性高于已报告数字的精度所暗示的程度——尤其是因为有些混杂因素实在太难控制。

在资源方法论标准化之前，我们的数据表明：若评测配置未被记录并匹配，排行榜上低于 3 个百分点的差异都应受到审慎质疑。Terminal-Bench 中等资源配置范围内观察到的差距略低于 2 个百分点。朴素二项置信区间本身已跨越 1 至 2 个百分点；我们在此记录的基础设施混杂因素是在此之上叠加，而非包含在其中。在资源分配范围的两端，差距达到 6 个百分点。

领先几个百分点可能意味着真实的能力差距——也可能只是虚拟机更大。
