用并行 Claude 团队构建 C 编译器

发布于 2026 年 2 月 5 日

我们让使用智能体团队的 Opus 4.6 构建一套 C 编译器，之后便（基本上）放手不管。以下是它让我们了解的自主软件开发未来。

非官方中文译文，仅供个人或获授权的内部阅读。 查看英文原文

    作者 Nicholas Carlini 是我们 Safeguards 团队的研究员。

    我一直在试验一种监督语言模型的新方法，我们称之为“智能体团队”。

    在智能体团队中，多个 Claude 实例无需活跃的人类干预，便可并行处理共享代码库。这种方法极大拓展了 LLM 智能体可实现目标的范围。

    为了压力测试该方法，我让 16 个智能体从零编写一个基于 Rust 的 C 编译器，要求能够编译 Linux 内核。历经近 2,000 个 Claude Code 会话、花费 20,000 美元 API 成本后，智能体团队产出了一个 10 万行的编译器，可在 x86、ARM 和 RISC-V 上构建 Linux 6.9。

    这个编译器本身是一个有趣的成果，但本文重点是我从为长时程自主智能体团队设计 harness 中学到的内容：如何编写无需人工监督也能让智能体保持正轨的测试，如何组织工作让多个智能体并行推进，以及这种方法的上限在哪里。

    让 Claude 长时间运行

    Claude Code 等现有智能体脚手架要求操作员在线并随时共同工作。如果你要求它解决一个漫长而复杂的问题，模型可能会完成一部分，但最终会停下并等待后续输入——一个问题、状态更新或澄清请求。

    为了引发持续、自主的进展，我构建了一个让 Claude 停留在简单循环中的 harness（如果你见过 Ralph-loop，这看起来应当很熟悉）。当它完成一项任务后，会立刻开始下一项。（请在容器中运行，而非在真实机器上运行。）

    #!/bin/bash

while true; do
    COMMIT=$(git rev-parse --short=6 HEAD)
    LOGFILE="agent_logs/agent_${COMMIT}.log"

    claude --dangerously-skip-permissions \
           -p "$(cat AGENT_PROMPT.md)" \
           --model claude-opus-X-Y &> "$LOGFILE"
done


    在智能体提示中，我告诉 Claude 需要解决的问题，并要求它将问题拆成小块、追踪当前工作、确定接下来做什么，并且有效地持续推进直到完美。（至于最后一点，Claude 没有选择。循环会永久运行——不过有一次，我确实看到 Claude 不小心 pkill -9 bash，结果杀死了自己并结束循环。哎呀！）


    并行运行 Claude

    并行运行多个实例能够解决单智能体 harness 的两个弱点：

    • 一个 Claude Code 会话一次只能做一件事。特别是随着项目范围扩展，同时调试多个问题效率高得多。
    • 运行多个 Claude 智能体可实现专业化。少数智能体负责解决手头实际问题，其他专业智能体则可承担维护文档、监控代码质量或解决专门子任务等工作。

    我的并行 Claude 实现非常简陋。先创建一个新的裸 git 仓库，再为每个智能体启动一个 Docker 容器，并将仓库挂载到 /upstream。每个智能体都克隆一份本地副本到 /workspace，完成后从其本地容器推送至上游。

    为防止两个智能体同时尝试解决同一问题，harness 使用简单的同步算法：

    1. Claude 通过向 current_tasks/ 写入文本文件来为任务加“锁”（例如，一个智能体可能锁定 current_tasks/parse_if_statement.txt，另一个锁定 current_tasks/codegen_function_definition.txt）。若两个智能体尝试认领同一任务，git 的同步会迫使第二个智能体选择不同任务。
    2. Claude 处理任务，然后从上游拉取、合并其他智能体的改动、推送自己的改动并移除锁。合并冲突很频繁，但 Claude 足够聪明，能自行处理。
    3. 无限智能体生成循环会在新的容器中启动一个新的 Claude Code 会话，随后循环重复。

    这是一项非常早期的研究原型。我尚未实现智能体间的其他通信方式，也不强制任何高层目标管理流程。我不使用编排智能体。

    相反，我让每个 Claude 智能体自行决定如何行动。多数情况下，Claude 会接手“下一个最显而易见”的问题。卡在 bug 上时，Claude 通常会维护一份持续更新的文档，记录失败方法与剩余任务。在项目的 git 仓库 中，你可阅读历史记录，观察它如何为不同任务加锁。

    与 Claude 智能体团队编程的经验

    脚手架会循环运行 Claude，但只有当 Claude 能辨别如何取得进展时，这个循环才有用。我的大多数精力都投入在设计 Claude 周围的环境——测试、环境和反馈——使它无需我的帮助也能定向。以下是我在编排多个 Claude 实例时发现最有帮助的方法。

    编写极高质量的测试

    Claude 会自主解决我交给它的任何问题。因此任务验证器必须近乎完美，否则 Claude 会解决错误的问题。改进测试 harness 需要寻找高质量编译器测试套件，为开源软件包编写验证器和构建脚本，观察 Claude 犯下的错误，并在识别出这些失败模式后设计新测试。

    例如，项目接近尾声时，Claude 每次实现新功能都频繁破坏已有功能。为此，我构建了持续集成流水线，并实施更严格的约束，让 Claude 能更好测试其工作，确保新提交不会破坏现有代码。

    设身处地为 Claude 着想

    我必须不断提醒自己，我是在为 Claude 而非自己编写这个测试 harness，这意味着要重新思考许多关于测试该如何传达结果的假设。

    例如，每个智能体都会被放入一个毫无上下文的新容器中，尤其在大型项目上，它会花费大量时间熟悉环境。甚至在测试之前，为帮助 Claude 自助，我加入了维护详尽 README 和进度文件的指示；这些文件应频繁更新当前状态。

    我还牢记语言模型存在固有局限，在此情形中需要围绕这些局限设计，包括：

    • 上下文窗口污染：测试 harness 不应打印成千上万无用字节。最多应打印几行输出，并把所有重要信息记录到文件中，以便 Claude 在需要时找到。日志文件应易于自动处理：如果存在错误，Claude 应写入 ERROR 并在同一行写明原因，以便 grep 找到。预先计算汇总统计信息也有帮助，免得 Claude 重算。
    • 时间盲：Claude 无法感知时间，若放任不管，它会乐意花数小时运行测试而非取得进展。harness 很少打印增量进度（避免污染上下文），并提供默认 --fast 选项，运行 1% 或 10% 的随机样本。此子样本对每个智能体是确定的、但跨 VM 随机，因此 Claude 仍会覆盖全部文件，且每个智能体都能完美识别回归。

    让并行化变得容易

    当有许多彼此不同的失败测试时，并行化很简单：每个智能体选择一个不同的失败测试处理。测试套件达到 99% 通过率后，每个智能体致力于让一个不同的小型开源项目（如 SQLite、Redis、libjpeg、MQuickJS、Lua）编译成功。

    但当智能体开始编译 Linux 内核时，它们卡住了。不同于拥有数百个独立测试的套件，编译 Linux 内核是一项巨型任务。每个智能体都会遇到同一 bug、修复那个 bug，然后覆盖彼此的修改。即便运行 16 个智能体也无济于事，因为它们都被困在解决同一任务。

    修复方法是使用 GCC 作为在线、已知正确的编译器预言机进行比对。我编写了新的测试 harness，随机地让 GCC 编译内核大部分部分，只让 Claude 的 C 编译器编译剩余文件。若内核能工作，则问题不在 Claude 所编译的文件子集；若失败，则可进一步通过让 GCC 重编译其中一些文件来缩小范围。这让每个智能体能够并行工作，修复不同文件中的不同 bug，直到 Claude 的编译器最终能编译全部文件。（在此成功后，仍需应用差分调试技术，找出共同失败但各自独立工作正常的文件对。）

    多种智能体角色

    并行化还可实现专业化。LLM 编写的代码常会重复实现现有功能，因此我指派一名智能体合并它发现的任何重复代码。我让另一名负责提高编译器本身性能，第三名负责输出高效编译代码。我要求另一名智能体从 Rust 开发者角度批评项目设计、作出结构调整以提升总体代码质量，还让另一名处理文档。

    压力测试智能体团队的极限

    该项目被设计为能力基准。我希望压力测试 LLM 在今天仅仅勉强能实现目标的极限，以帮助我们为模型未来能够可靠实现的目标作准备。

    我一直使用 C 编译器项目作为整个 Claude 4 模型系列的基准。和此前项目一样，我先起草所需目标：从零开始的优化编译器、无依赖、与 GCC 兼容、能编译 Linux 内核，并设计为支持多个后端。虽然我指定了设计的一些方面（例如应有 SSA IR 以支持多次优化），却没有详细说明如何实现。

    此前的 Opus 4 模型仅勉强能够产出可用编译器。Opus 4.5 首次跨过阈值，能产出可通过大型测试套件的可用编译器，但仍无法编译任何真正的大型项目。使用 Opus 4.6 的目标是再次测试极限。

    评估

    在两周内近 2,000 个 Claude Code 会话中，Opus 4.6 消耗了 20 亿输入 token、生成 1.4 亿输出 token，总成本略低于 20,000 美元。即使与最昂贵的 Claude Max 套餐相比，这也是极其昂贵的项目。但这笔总成本只是我自己产出它——更不用说整个团队——所需成本的一小部分。

    这是一个净室实现（Claude 在开发的任何时候都不能访问互联网）；它仅依赖 Rust 标准库。这个 10 万行编译器可在 x86、ARM 和 RISC-V 上构建可启动的 Linux 6.9，也能编译 QEMU、FFmpeg、SQLite、postgres、redis，并在多数编译器测试套件上达到 99% 通过率，包括 GCC torture 测试套件。它还通过了开发者的终极试金石：能够编译并运行 Doom。

    不过，这个编译器并非没有局限，包括：

    • 它缺少启动 Linux 脱离实模式所必需的 16 位 x86 编译器。为此，它会调用 GCC（x86_32 和 x86_64 编译器由它自己实现）。
    • 它没有自己的汇编器和链接器；这是 Claude 最后开始自动化的部分，且仍存在一些 bug。演示视频使用 GCC 汇编器和链接器制作。
    • 该编译器能成功构建许多项目，但并非全部。它尚不能替代真实编译器。
    • 生成的代码效率不高。即便启用所有优化，它输出的代码也比禁用全部优化的 GCC 生成的代码效率更低。
    • Rust 代码质量尚可，但远达不到专家 Rust 程序员可能产出的质量。

    生成的编译器已接近 Opus 能力的极限。我曾（非常努力地）尝试修复上面几项限制，但没有完全成功。新功能和 bug 修复经常破坏现有功能。

    举一个尤其困难的例子，Opus 无法实现启动进入 16 位实模式所需的 16 位 x86 代码生成器。尽管编译器可通过 66/67 操作码前缀输出正确的 16 位 x86，编译结果却超过 60kb，远高于 Linux 强制的 32k 代码上限。因此 Claude 只能在此阶段取巧，调用 GCC（仅 x86 如此；对于 ARM 或 RISC-V，Claude 的编译器能够完全自行编译。）

    该编译器的 源代码已公开。下载它，阅读代码，并在你最喜欢的 C 项目上试用。我始终发现，理解语言模型能做什么的最佳方式，是将它们推到极限，然后研究它们从何处开始失效。未来几天，如你想继续关注 Claude 对解决这些限制的持续尝试，我会继续让 Claude 推送新的改动。

    展望未来

    每一代语言模型都带来与之协作的新方式。早期模型适合 IDE 中的 Tab 补全。不久后，模型可根据 docstring 补全函数体。Claude Code 的发布让智能体进入主流，也使开发者能与 Claude 结对编程。但这些产品都基于同一假设：用户定义任务，LLM 运行数秒或数分钟并返回答案，然后用户再提供后续输入。

    智能体团队展示了自主实现整个复杂项目的可能性。这让作为这些工具使用者的我们，可以为目标设得更宏大。

    我们仍处于早期，完全自主开发伴随真实风险。人类与 Claude 一同开发时，可确保质量一致并实时捕捉错误。对自主系统而言，很容易看到测试通过便假定工作已经完成，但现实很少如此。我曾从事渗透测试，利用大公司产品中的漏洞；想到程序员部署自己从未亲自验证的软件，确实令人担忧。

    因此，这项实验令我兴奋，也令我不安。构建这个编译器是我近期最有趣的经历之一，但我没想到在 2026 年初就已接近可行。语言模型与我们用来和它们交互的脚手架都在快速进步，这为编写海量新代码打开大门。我预计正面应用会超过负面影响，但我们正进入一个需要新策略才能安全应对的新世界。
