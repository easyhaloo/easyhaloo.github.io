设计能抵御 AI 的技术评估

发布于 2026 年 1 月 21 日

我们从一个 Claude 不断击败的性能工程居家作业的三次迭代中学到什么。

非官方中文译文，仅供个人或获授权的内部阅读。 查看英文原文

作者 Tristan Hume 是 Anthropic 性能优化团队负责人。他设计并重新设计了帮助 Anthropic 招聘数十名性能工程师的居家作业测试。

随着 AI 能力提升，评估技术候选人变得更难。今天能很好区分人类技能水平的居家作业，明天可能被模型轻易解决，从而失去评估价值。

自 2024 年初以来，我们的性能工程团队一直使用一项居家作业：候选人需为模拟加速器优化代码。已有逾 1,000 名候选人完成该测试，数十人如今在此工作，其中包括启动我们的 Trainium 集群并发布 Claude 3 Opus 以来每个模型的工程师。

但每个新 Claude 模型都迫使我们重新设计测试。在给定相同时间限制下，Claude Opus 4 的表现超过大多数人类申请者。这仍能让我们区分最强候选人——但 Claude Opus 4.5 随后也匹配了他们。人在无限时间下仍可胜过模型，但在居家作业限制下，我们不再能区分顶尖候选人和最强模型的输出。

我现已对居家作业迭代三个版本，试图确保它仍带有信号。每次，我都学到关于什么能让评估抵御 AI 辅助、什么不能的新内容。

本文介绍原始居家作业设计、每个 Claude 模型如何击败它，以及为让测试领先顶尖模型能力，我不得不采取的日益非常规的方法。尽管我们的工作随模型演进，我们仍需要更多优秀工程师——只是寻找他们的方法必须更具创造力。

为此，我们将原始居家作业作为公开挑战发布；因为在无限时间下，最优秀的人类表现仍超过 Claude 可实现的水平。若你能胜过 Opus 4.5，我们很期待听到你的消息——详情在文末。

居家作业的起源

2023 年 11 月，我们正准备训练和发布 Claude Opus 3。我们已获得新的 TPU 和 GPU 集群，大型 Trainium 集群即将到位，并在加速器上的投入远超以往，但新规模下没有足够的性能工程师。我在 Twitter 上发帖邀请人们发邮件给我们。这带来了比标准面试流程可评估更多的有希望候选人，而该流程对员工和候选人均消耗大量时间。

我们需要一种更高效评估候选人的方法。因此，我花两周设计一份居家作业测试，既能充分涵盖岗位需求，又能识别最有能力的申请者。

设计目标

居家作业名声不佳。它们通常充满工程师觉得无聊的通用问题，也是不佳筛选器。我的目标不同：创造真正引人入胜的内容，让候选人兴奋参与，并使我们能以高分辨率捕捉他们的技术能力。

与现场面试相比，这种形式评估性能工程技能也有优势：

更长时间跨度：工程师编程时很少面对少于一小时的截止时间。4 小时窗口（后来减至 2 小时）更能反映工作的实际性质。它仍短于大多数真实任务，但我们需要权衡其负担。

真实环境：无人观看或期待讲解。候选人在自己的编辑器中无干扰地工作。

理解与工具开发时间：性能优化需要理解现有系统，有时还需构建调试工具。二者都很难在普通的 50 分钟面试中真实评估。

与 AI 辅助兼容：Anthropic 的 通用候选人指南要求候选人除非另有说明，否则在无 AI 条件下完成居家作业。对于这项居家作业，我们明确作出不同说明。

时间跨度更长的问题更难被 AI 完全解决，因此候选人可使用 AI 工具（如在工作中一样），同时仍需展示自己的技能。

除这些形式特定目标外，我还采用设计任何面试时使用的同一原则，让居家作业具备：

代表真实工作：问题应让候选人体验岗位实际涉及的内容。

高信号：居家作业应避免依赖单一洞见的问题，并确保候选人有许多机会展示完整能力——尽量少交给运气。它还应有宽广的分数分布和足够深度，即使强候选人也无法完成全部内容。

无需特定领域知识：基本功优秀的人可在工作中学习细节。要求狭窄专长会不必要地限制候选人池。

有趣：快速开发循环、有深度的有趣问题，以及创造空间。

模拟机器

我为一个特性类似 TPU 的虚构加速器构建了 Python 模拟器。候选人要优化此机器上运行的代码，并使用热重载 Perfetto跟踪，它会展示每条指令，类似于 我们在 Trainium 上使用的工具。.

该机器具有使加速器优化有趣的特性：手动管理的暂存内存（不同于 CPU，加速器常要求显式内存管理）、VLIW（每周期多个执行单元并行运行，需高效打包指令）、SIMD（每条指令对许多元素进行向量操作）和多核（将工作分布至内核）。

任务是并行树遍历，刻意不采用深度学习风格，因为多数性能工程师尚未接触深度学习，领域细节可在工作中学习。该问题受无分支 SIMD 决策树推理启发，是一个向过去致敬的经典 ML 优化挑战，先前仅少数候选人遇到。

候选人从全串行实现开始，逐步利用机器并行性。热身是多核并行，随后候选人选择处理 SIMD 向量化或 VLIW 指令打包。原始版本还含一个候选人需先调试的 bug，以检验其构建工具能力。


早期结果

最初居家作业效果良好。Twitter 批次中有一人得分显著高于其他所有人。他在我们通过标准流程首次招聘两周后，于 2 月初入职。测试具有预测力：他很快开始优化 kernel，并找到一个解决启动阻塞编译器 bug 的办法，该 bug 涉及张量索引数学溢出 32 位。

接下来一年半，约 1,000 名候选人完成居家作业，它帮助我们招聘了当前性能工程团队的大多数成员。它对履历经验有限候选人尤其有价值：数名最高绩效工程师直接来自本科，但在居家作业中展现足够技能，让我们有信心聘用。

反馈积极。许多候选人因享受其中而超过 4 小时限制继续工作。最强的无限时间提交包含完整优化微型编译器，以及一些我未曾预料的巧妙优化。

随后 Claude Opus 4 击败了它

到 2025 年 5 月，Claude 3.7 Sonnet 已接近这样一个程度：超过 50% 的候选人若将任务完全委派给 Claude Code 会更有利。我随后用居家作业测试了预发布 Claude Opus 4。它在 4 小时时限内得出的优化解法，比几乎所有人类都更好。

这不是第一次有 Claude 模型击败我设计的面试。2023 年，我专门设计一道现场面试题，因为当时的问题基于早期 Claude 模型很熟悉、因而易解的常见任务。我尝试设计一道比知识更需解题能力、但仍基于我在工作中解决的真实（但小众）问题的题目。Claude 3 Opus 击败了该题第一部分；Claude 3.5 Sonnet 击败第二部分。我们仍在使用它，因为其他现场题目也无法抵御 AI。

对于居家作业，修复相当直接。问题的深度远超任何人在 4 小时内可探索范围，因此我利用 Claude Opus 4 找出它开始遇到困难之处。这成为版本 2 的新起点。我编写更干净的起始代码，添加新机器特性以增加深度，并移除多核（Claude 已解决它，而它只会拖慢开发循环、不增加信号）。

我还将时间限制从 4 小时缩短到 2 小时。最初选择 4 小时是基于候选人反馈，他们希望在 bug 或困惑上卡一会时少一些完全沉没的风险；但排期开销让流程延迟数周。两小时更容易塞进周末。

版本 2 强调巧妙优化洞见，而非调试和代码量。它很好地服务了我们——数月之久。

随后 Claude Opus 4.5 击败了它

当我测试预发布 Claude Opus 4.5 检查点时，我观察 Claude Code 用两小时处理问题，逐步改善其解法。它解决初始瓶颈、实现所有常见微优化，并在一小时内达到我们的通过阈值。

随后它停下，确信自己遇到无法逾越的内存带宽瓶颈。大多数人类也得出同一结论。但存在利用问题结构绕过该瓶颈的巧妙技巧。当我告诉 Claude 可达到的周期数时，它思考了一会并找到了技巧。然后它调试、调优并实现进一步优化。两小时节点上，它的得分匹配这一时限内最好的人类表现——而该人类还大量使用 Claude 4 进行引导。

我们在内部测试时计算 harness 中试用了它以获得更严谨结果，确认它既能在 2 小时内胜过人类，又能随时间继续攀升。发布后，我们甚至以通用方式改进 harness，得到更高分。

我遇到问题了。我们即将发布一个模型，在居家作业上最好的策略将是委派给 Claude Code。


考虑选项

一些同事建议禁止 AI 辅助。我不想这样做。除了执行挑战外，我感觉既然人在工作中继续发挥关键作用，就应能想出 某种让他们在 有 AI 的环境中脱颖而出的办法——这种环境正是他们在工作中面对的。我还不想屈服于这样的 观点

：人类仅在时长超过数小时的任务上具备优势。

如今 Anthropic 的性能工程师仍有大量工作要做，但它更像困难调试、系统设计、性能分析、弄清如何验证系统正确性，以及让 Claude 的代码更简单、更优雅。不幸的是，没有大量时间或共同上下文，很难以客观方式测试这些事。设计能代表工作的面试一直很难，如今比以往更难。

但我也担心，如果投入设计新的居家作业，Claude Opus 4.5 要么也会解决它，要么它会变得过难，使人类不可能在两小时内完成。

尝试 1：另一道优化问题

我意识到 Claude 可快速实现我设计的任何内容，这促使我尝试开发更难的居家作业。我选择一个基于自己在 Anthropic 做过的较棘手 kernel 优化的问题：高效数据 转置，即在二维 TPU 寄存器上进行转置，同时避免 bank 冲突。我将它提炼为模拟机器上的更简单问题，并让 Claude 在不到一天内实现改动。

Claude Opus 4.5 找到了一项我甚至未想过的出色优化。经过仔细分析，它意识到可转置整个计算，而非设法转置数据，于是相应重写整个程序。

在我的真实案例中，这行不通，因此我修补问题以去除该方法。Claude 随后取得进展，却找不到最高效解法。似乎我有了新问题，只需希望人类候选人能足够快地完成。但我心存疑虑，于是用 Claude Code 的“ultrathink”功能及更长思考预算复查……它解决了。它甚至知道修复 bank 冲突的技巧。

事后看来，这不是合适的尝试问题。许多平台的工程师都曾解决数据转置与 bank 冲突，因此 Claude 有大量训练数据可借鉴。虽然我是从第一性原理找到解法，Claude 却能调用更大的经验工具箱。

尝试 2：变得更古怪

我需要一个人类推理能胜过 Claude 更大经验基础的问题：某个足够分布外的内容。不幸的是，这与我希望它明显类似于工作的目标冲突。

我思考了自己喜欢过的最不寻常优化问题，最终选中 Zachtronics 游戏。这些编程解谜游戏采用不寻常、强约束的指令集，迫使玩家以非常规方式编程。例如，在 Shenzhen I/O中，程序被拆分到多个通信芯片，每个芯片仅能容纳约 10 条指令与一两个状态寄存器。巧妙优化往往涉及将状态编码进指令指针或分支标志。

我设计了一项新居家作业，由使用微小、高度约束指令集的谜题构成，目标是将指令数优化到最少。我实现一道中等难度谜题并用 Claude Opus 4.5 测试，它失败了。我增加更多谜题，并让同事验证不如我熟悉问题的人仍能胜过 Claude。

与 Zachtronics 游戏不同，我特意不提供可视化或调试工具。起始代码只检查解法是否有效。构建调试工具本身就是被测试内容：你可以插入精心设计的 print 语句，或让编码模型在几分钟内生成交互式调试器。判断如何投入工具开发也是信号的一部分。

我对新居家作业还算满意。因其由更多独立子问题组成，方差可能低于原版。早期结果很有希望：分数与候选人过去工作水准相关良好，我最有能力的一名同事得分高于迄今所有候选人。

我仍为放弃原版的真实感和多样深度感到遗憾。但真实感可能是我们不再拥有的奢侈。原版有效，因为它类似真实工作；替代版有效，因为它模拟新颖工作。


公开挑战

我们发布原始居家作业，供任何人以无限时间尝试。人类专家 仍保有优势，可在足够长的时间跨度上胜过当前模型。史上提交的最快人类解法，大幅超过 Claude 即使使用广泛测试时计算所达到的表现。

发布版本从零开始（如版本 1），但采用版本 2 的指令集和单核设计，因此周期数与版本 2 可比。

性能基准（以模拟机器时钟周期计）：

  • 2164 个周期：Claude Opus 4 在测试时计算 harness 中运行许多小时后
  • 1790 个周期：Claude Opus 4.5 在普通 Claude Code 会话中，约匹配人类两小时内最佳表现
  • 1579 个周期：Claude Opus 4.5 在我们的测试时计算 harness 中运行两小时后
  • 1548 个周期：Claude Sonnet 4.5 进行远超两小时的测试时计算后
  • 1487 个周期：Claude Opus 4.5 在 harness 中运行 11.5 小时后
  • 1363 个周期：Claude Opus 4.5 在改进的测试时计算 harness 中运行许多小时后

在 GitHub 上下载。若你将其优化至低于 1487 个周期，胜过 Claude 在发布时的最佳表现，请将代码和简历发送至 performance-recruiting@anthropic.com。

或者，你也可以 通过我们的常规流程申请，该流程使用我们现在的抗 Claude 居家作业。我们很想知道它能持续多久。
